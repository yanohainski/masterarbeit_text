\section{Nachweis der Machbarkeit (Proof of Concept)}
Zur Validierung der grundsätzlichen Machbarkeit des Systems wurde zunächst ein einfaches Proof of Concept (PoC) entwickelt. Dieses entstand in Form eines Python-basierten Jupyter-Notebooks und diente dazu, die Kernannahmen des Projekts frühzeitig zu überprüfen.

Der PoC verband den aus der Masterprojektarbeit (MPA) bereits entwickeltem Speech-to-Text-Service mit einem Large Language Model, um transkribierte Audiodaten direkt weiterzuverarbeiten und zusammenzufassen. Hierfür wurden Audiodaten manuell erzeugt, in das erforderliche WAV-Format überführt und schrittweise an den Transkriptionsdienst übergeben.

Im Rahmen dieses Prototypen konnten folgende Aspekte erfolgreich validiert werden: 

\begin{itemize}
    \item grundsätzliche Funktionsfähigkeit der Transkriptionspipeline
    \item Anbindung eines LLM zur Analyse der Transkripte
    \item Erzeugung erster inkrementeller Zusammenfassungen
\end{itemize}

Gleichzeitig traten während der Entwicklung des ersten PoC früh technische Herausforderungen auf, insbesondere im Bereich der Parallelisierung und Thread-Verwaltung. Die Verarbeitungsschritte für Audioaufnahme, Transkription und LLM-Anfrage wurden zunächst sequentiell implmenentiert. In der Praxis zeigte sich, dass durch die Inferenzzeit des STT-Services sowie des LLM-Aufrufes zur Analyse des Transkripts die Weiteraufnahme von Audiofiles blockiert wurde. Dadurch konnte keine kontinuierlichen Audioaufnahmen erstellt werden, was zu Lücken im Kontext führte. 

Zusätzlich verfügt das LLM kein Sitzungs- oder Prozessgedächtniss. Jede Anfrage wird isoliert behandelt, sodass Kontextinformationen zwischen den Aufrufen verloren gehen. 

Diese Erkenntnisse bestätigten die Notwendigkeit einer asynchronen, entkoppelten Backend-Architektur mit einer persistenten Datenverwaltung der LLM-Ergebnisse und flossen direkt in die weitere Systemgestaltung ein. 

\section{Integration in die bestehende Backend-Struktur}
Das Notisent-Backend folgt dem App-Konzept von Django, bei dem funktional zusammengehörige Logik in klar abgegrenzten Modulen organisiert ist. Für den Meetingassistenten wurde eine eigene App implementiert, die sämtliche Logik zur Verarbeitung von Meeting-Transkripten, zur Steuerung der Analyseprozesse sowie zur Kommunikation mit dem Frontend kapselt. 

Diese App wird nicht isoliert betrieben, sondern greift auf zentrale Backend-Komponenten von Notisent zurück. Dazu zählen insbesondere: 

\begin{itemize}
    \item die bestehende Authentifizierungs- und Benutzerverwaltung
    \item der Zugriff auf persistente Datenbanken.
    \item die API-Anbindung an extern gehostete KI-Modelle, die von der Notisent-Infrastruktur genutzt werden.
\end{itemize}

Durch diese Integration konnte vermieden werden, parallele oder redundante Backend-Strukturen aufzubauen.

\subsection{Teams Bot}
Wie bereits in \ref{sec:attendee} beschrieben, wird zum Erfassen der relevanten Meetingdaten die Open-Source API Attendee verwendet. Die Erfassung der Transkriptdaten erfolgt über einen Meeting-Bot, welcher in Microsoft-Teams-Sitzungen eingebunden wird und sich wie ein normaler Teilnehmer verhält. Der Bot wird über eine REST-Schnittstelle erstellt und verwaltet. Listing \ref{lst:example_startbot_message} zeigt eine beispielhafte Nachricht zum Starten des Bots. Die Aufgabe des Bots beschränkt sich auf die Teilnahme am Meeting und Übermittelung von Transkriptdaten.

Nach dem Start des Meetings übernimmt der Bot folgende Aufgaben: 
\begin{itemize}
    \item Beitritt zur Konferenz
    \item Erfassung der gesprochenen Inhalte
    \item Übertragung von Transkriptionsereignissen an das Backend
    \item Meldung von Statusänderungen
    \item Übermittlung von Teilnehmerereignissen
\end{itemize}

Ein Bot wird über die Attendee-API durch einen HTTP-Post-Request and den Endpoint \textbf{/api/v1/bots} erstellt. Im JSON-Body der Nachricht müssen die Meeting-URL, ein Botname sowie ein API-Token zur Authentifizierung enthalten sein. Die Antwort enthält eine eindeutige Bot-ID, über welche anschließend der Status abgefragt oder Transkriptabrufe durchgeführt werden. Dazu wurde im Backend unter views.py die Klasse \texttt{CreateMeetingBotView} erstellt, welche sich um die Boterstellung kümmert. In Listing \ref{lst:example_startbot_message} ist eine Beispielhaft der JSON-Body einer solchen Nachricht zu sehen.

Eine View-Klasse in Django stellt die serverseitige Verarbeitungssschicht eines HTTP-Endpoints dar. Sie nimmt eingehende Requests entgegen, validiert die Daten, führt die Geschäftslogik aus und erzeugt anschließend die HTTP-Response. In diesem Fall kapselt die Klasse \texttt{CreateMeetingBotView} die komplette Logik zur Erstellung des Bots. Sie verarbeitet den POST-Request auf \textbf{/api/v1/bots}, prüft Meeting-URL, Botnamen und API-Token, startet den Bot über die Attendee-API und gibt die erzeugte Bot-ID im Response zurück.

Die Kommunikation zwischen Bot und Backend erfolgt ausschließlich über Webhooks. Diese Architektur stellt sicher, dass der Bot selbst keine Geschäftslogik enthält und lediglich als Datenquelle fungiert. Sämtliche Verarbeitungsschritte, von der Zwischenspeicherung bis zur Zusammenfassung, werden severseitig durchgeführt. Ein Vorteil dieses Ansatzes liegt in der Austauschbarkeit des Bot-Systems. Das Backend verarbeitet lediglich standardisierte Ereignisse, wodurch der Bot prinzipiell durch andere Anbieter oder Plattformen ersetzt werden kann, ohne weitere Anpassung der Kernlogik.

Für die Kommunikation zwischen dem lokal betriebenen Attendee-Dienst und dem ebenfalls lokalen laufenden Backend wird während der Entwicklung der Tunneling-Dienst \textit{ngrok} eingesetzt. Attendee setzt für die Übermittelung der Ergebnisse eine öffentlich erreichbare HTTPS-Endpoint-Adresse voraus. 
Der Einsatz ist erforderlich, da Attendee zur Ergebnisübermittelung einen Webhook mit einer Verschlüsselten HTTPS-Verbindung benötigt und nicht an eine HTTP-Verbindung senden kann. Da das lokale Backend standardmäßig nur über HTTP innerhalb des Docker- bzw. Host-Netzwerks erreichbar ist, kann Attendee diesen Endpoint ohne Weiteres nicht ansprechen. Ngrok stellt hierfür temporär einen sicheren HTTPS-Tunnel bereit, der eingehende Webhook-Anfragen an das lokale Backend weiterleitet.

Im produktiven Betrieb ist dieser Zwischenschritt nicht erforderlich, da das Backend dort direkt über eine reguläre HTTPS-Infrastruktur erreichbar ist.

Jede eingehende Nachricht im Webhook wird auf ihren Trigger untersucht und entsprechend verarbeitet. Listing \ref{lst:message_filter} zeigt den Aufbau der Funktion.

\newpage
\begin{lstlisting}[language=python, style=pythonstyle, caption=Filterfunktion für Eingehende Nachrichten, label=lst:message_filter]
class MeetingBotWebhook(APIView):
    """
    HTTP Webhook endpoint for receiving meeting events from external bot service.

    Handles three trigger types:
    - bot.stage_change: Meeting lifecycle events
    - transcript.update: New speech transcribed
    - participant_events.join_leave: Participant activity
    """

    parser_classes = [JSONParser]
    permission_classes = [AllowAny]

    @swagger_auto_schema(tags=["voice"])
    def post(self, request, *args, **kwargs):
        """Handle incoming meeting webhook messages"""
        try:
            payload = request.data
            trigger = payload.get("trigger", "unknown")
            bot_id = payload.get("bot_id", "unknown")
            data = payload.get("data", {})

            if not trigger or not bot_id:
                logger.error("Missing required fields: trigger or bot_id")
                return Response(
                    {"error": "Missing required fields: trigger and bot_id"},
                    status=http_status.HTTP_400_BAD_REQUEST,
                )
            logger.info(f"Received webhook event '{trigger}' for bot '{bot_id}'")

            # Dispatch to appropriate handler
            if trigger == "bot.stage_change":
                return self._handle_stage_change(bot_id, data)
            elif trigger == "transcript.update":
                return self._handle_transcript_update(bot_id, data)
            elif trigger == "participant_events.join_leave":
                return self._handle_participant_event(bot_id, data)
            else:
                logger.warning(f"Unknown trigger type: {trigger}")
                return Response(
                    {"status": "received", "message": f"Unknown trigger: {trigger}"},
                    status=http_status.HTTP_200_OK,
                )

        except Exception as e:
            logger.error(f"Error processing webhook: {str(e)}", exc_info=True)
            return Response(
                {"error": "Failed to process webhook data"},
                status=http_status.HTTP_500_INTERNAL_SERVER_ERROR,
            )
\end{lstlisting}

Nachrichten mit dem \texttt{transcript.update} Trigger werden von der in Listing \ref{lst:handletranscript} aufgeführten Funktion \texttt{handle\_transcript update} verarbeitet. 
Dabei wird jede Nachricht auf ihre zeitliche Länge untersucht. Nachrichten werden in einer Redis-Warteschlange gesammelt. Die Logik dahinter ist in Listing \ref{lst:handletranscript} zu sehen.

    def _handle_transcript_update(self, bot_id: str, data: Dict) -> Response:
        """Handle transcript.update events"""
        duration = data.get("duration_ms", 0)
        speaker_name = data.get("speaker_name", "Unknown")
        speaker_is_host = data.get("speaker_is_host", False)
        timestamp = data.get("timestamp_ms", "")
        transcription_obj = data.get("transcription", {})
        transcript = transcription_obj.get("transcript", "")

        logger.info(
            f"Transcript update - Speaker: {speaker_name}, "
            f"Host: {speaker_is_host}, Duration: {duration}ms"
            f"Transcript: {transcript}..."
        )

        # Create message and add to queue
        queued_message = {
            "duration_ms": duration,
            "speaker_name": speaker_name,
            "speaker_is_host": speaker_is_host,
            "timestamp_ms": timestamp,
            "transcription": transcription_obj,
        }

        message_queue.add_to_queue(
            bot_id=bot_id,
            message=queued_message,
            process_callback=process_message_batch,
        )

        return Response(status=http_status.HTTP_200_OK)
\end{lstlisting}

Sobald die gesammelten Transkriptsegmente eine definierte Schwelle überschreiten, in diesem Fall eine Gesamtlänge größer zehn Sekunden, werden sie zu einem zusammenhängenden Textblock aggregiert und zur weiteren Analyse vorbereitet. Diese Aggregation bildet die Grundlage für die inkrementelle Zusammenfassung im Rahmen der Rolling-Summary-Strategie.

\subsection{Anbindung der Analyse- und KI-Komponenten}

Die eigentliche Analyse der Textdaten erfolgt über eine API-basierte Anbindung an externe KI-Modelle. Das Backend bereitet die aggregierten Transkriptsegmente auf, ergänzt sie um den aktuellen Stand der vorherigen Zusammenfassung und übergibt diese Daten an die KI-Schnittstelle. In Listing \ref{lst:processbatch} ist dieser Vorgang im Code dargestellt. 

Die Rückgabe des Modells, in Form einer aktualisierten Zusammenfassung, wird vom Backend entgegengenommen, validiert und sowohl temporär zwischengespeichert als auch für die Weitergabe an das Frontend vorbereitet. Auf diese Weise entsteht eine fortlaufende aktualisierte Gesamtzusammenfassung des Meetings, die den aktuellen Gesprächsstand widerspiegelt.

\begin{lstlisting}[language=python, style=pythonstyle, caption=Verarbeitung der Redis-Warteschlange, label=lst:processbatch]
def process_message_batch(bot_id: str, messages: List[Dict]) -> str:
    """
    Process batch of messages and generate/update summary.
    This is the callback triggered when message queue threshold is exceeded.

    Args:
        bot_id: The bot identifier
        messages: List of message dictionaries to process

    Returns:
        Generated summary text
    """
    logger.info(f"Processing {len(messages)} messages for bot {bot_id}")

    # Build conversation transcript from batch
    conversation_lines = _build_conversation_transcript(bot_id, messages)
    new_transcript = "\n".join(conversation_lines)

    logger.info(f"Transcript:\n{new_transcript}")

    # Get previous summary from cache
    previous_summary = get_cached_summary(bot_id)

    tenant_id = "123445"  # Placeholder tenant ID
    ms_user_id = "user_67890"  # Placeholder user ID

    # Generate new summary using LLM
    summary = create_rolling_summary(
        new_transcript=new_transcript,
        previous_summary=previous_summary,
        tenant_id=tenant_id,
        ms_user_id=ms_user_id,
    )

    # Update cache
    update_cached_summary(bot_id, summary)

    # Persist to database
    Meeting.objects.create(
        bot_id=bot_id,
        tenant_id=tenant_id,
        ms_user_id=ms_user_id,
        summary_text=summary,
    )

    logger.info(f"Persisted summary for bot {bot_id} to database")
    # Broadcast to WebSocket clients
    broadcast_summary(bot_id, summary)

    logger.info(f"Generated Summary for bot {bot_id}:\n{summary}")
    return summary

\end{lstlisting}

\subsection{Prompting und Analyse des Transkripts}
Im Rahmen der Implementierung wurde ein promptbasiertes Verfahren zur Verarbeitung kontinuierlich eingehender Sprachtranskripte entwickelt, das eine inkrementelle Zusammenfassung im Sinne eines Rolling-Summary-Mechanismus realisiert. Ziel dieses Ansatzes ist es, neu eintreffende Transkriptsegmente schrittweise in eine bestehende Gesamtzusammenfassung zu integrieren, ohne den zuvor aufgebauten semantischen Kontext zu verlieren. Dadurch wird eine fortlaufende Verdichtung der Inhalte ermöglicht, während gleichzeitig die Kontextlänge und damit die Eingabekomplexität für das Sprachmodell kontrolliert bleibt. In Listing \ref{lst:prompting} ist ein Auszug aus dem \texttt{llm.py} zu sehen, welcher das Prompting und Erstellen der Rolling Summary zeigt.

Die Modellinteraktion erfolgt über das Framework DSPy, welches eine strukturierte Definition und Ausführung von Prompts für Large Language Models erlaubt. Zentrales Element ist eine dedizierte Prompt-Struktur, die explizit festlegt, welche Eingaben dem Modell übergeben werden, insbesondere das aktuelle Transkriptsegment sowie die bisherige Teilzusammenfassung und welches Ausgabeformat erwartet wird. Die formale Spezifikation wird über eine von \texttt{dspy.Signature} abgeleitete Klasse realisiert, wodurch Ein- und Ausgaben typisiert, reproduzierbar und konsistent verarbeitet werden können.

\texttt{dspy.Signature} beschreibt dabei die Schnittstelle zum Sprachmodell in Form deklarierter Ein- und Ausgabefelder. Diese strukturierte Definition ersetzt frei formulierte Prompt-Strings, ermöglicht eine automatische Serialisierung der Eingaben sowie ein konsistentes Parsen der Ausgaben und stellt so eine stabile, wiederverwendbare Modellinteraktion sicher. Anstatt einen Prompt als frei zusammengesetzten String zu formulieren, werden strukturierte Felder wie \texttt{previous\_summary} \texttt{voice\_content} und \texttt{summary} definiert. DSPy übernimmt anschließend automatisch die Serialisierung dieser Felder in ein Prompt-Format und sorgt dafür, dass die Modellantwort wieder in die definierten Output-Felder geparst wird.

Ein \texttt{dspy.Module} bildet die ausführbare Einheit der Modellinteraktion und kapselt die Verarbeitungsschritte eines Sprachmodellaufrufs. Auf Basis einer definierten \texttt{Signature} übernimmt ein Modul automatisch die Erstellung des Prompts, die Anfrage an das konfigurierte LLM sowie die strukturierte Aufbereitung der Rückgabe. Dadurch wird die Modellnutzung als wiederverwendbare, funktionale Operation abstrahiert, anstatt jeden Aufruf manuell zu implementieren. 

Der Wrapper \texttt{dspy.context} dient der temporären Konfiguration des verwendeten Sprachmodells für einen klar abgegrenzten Ausführungsbereich. Innerhalb des with-Blocks wird das Standard-LLM durch eine spezifische Instanz ersetzt, ohne globale Einstellungen oder andere Modellaufrufe zu beeinflussen. Dadurch lässt sich das Verhalten einzelner Requests gezielt steuern, während der restliche Anwendungskontext unverändert bleibt.

Die Funktion \texttt{lm\_with\_extra\_body} erweitert das Modellobjekt dabei um zusätzliche Metadaten, etwa Mandanten-, Nutzer- oder Request-IDs. Diese Informationen werden nicht Teil des eigentlichen Prompts, sondern ausschließlich auf Transport- bzw. Logging-Ebene an die Anfrage angehängt.

Die Verantwortlichkeiten innerhalb der Implementierung sind modular organisiert. Das Modul llm.py kapselt sämtliche Interaktionen mit dem Sprachmodell, einschließlich der Prompt-Definition, der Vorverarbeitung der Eingabedaten sowie der Durchführung der Analyseaufrufe. Zur Verwaltung des fortlaufenden Kontexts werden erzeugte Teilzusammenfassungen in \texttt{cache.py} zwischengespeichert und bei nachfolgenden Modellaufrufen erneut eingebunden. Diese Form der Kontextverwaltung gewährleistet, dass frühere Informationen verfügbar bleiben und gleichzeitig die effektive Tokenlänge kontrolliert wird.

\begin{lstlisting}[language=python, style=pythonstyle, caption=Aufruf des LLM und Erstellung der Rolling Summary, label=lst:prompting]
class VoiceSummarySignature(dspy.Signature):
    """Fasse den Inhalt der Sprachnachricht zusammen."""

    extra_instructions: str = dspy.InputField()
    previous_summary: str = dspy.InputField(desc="Bisherige Zusammenfassung")
    voice_content: str = dspy.InputField()
    summary: str = dspy.OutputField(desc="Kurze, praezise Zusammenfassung")


def _get_voice_summarizer() -> dspy.Module:
    """Get or create the voice summarizer module"""
    global _voice_summarizer
    if _voice_summarizer is None:
        _voice_summarizer = dspy.Predict(VoiceSummarySignature)
    return _voice_summarizer


def create_rolling_summary(
    new_transcript: str, previous_summary: str, tenant_id: str, ms_user_id: str
) -> str:
    """
    Generate or update summary with new transcript chunk using LLM.

    Args:
        new_transcript: The new transcript text to summarize
        previous_summary: The existing summary to build upon
        tenant_id: Tenant identifier for tracking
        ms_user_id: User identifier for tracking

    Returns:
        Updated summary text
    """

    instructions = (
        "Du bist ein Spezialist fuer Meeting-Zusammenfassungen. "
        "Aktualisiere die bestehende Zusammenfassung mit den neuen Informationen. "
        "Behalte die vorherige Zusammenfassung und haenge die neuen Informationen an. "
        "Entferne Redundanzen und halte die Zusammenfassung praezise und strukturiert. "
        "Wenn dies der erste Chunk ist (previous_summary ist leer), erstelle eine neue Zusammenfassung. "

    )

    try:
        logger.info("Generating rolling summary for new transcript chunk")

        predictor = _get_voice_summarizer()

        meta = {
            "tenant_id": tenant_id,
            "ms_user_id": ms_user_id,
            "request_id": str(uuid.uuid4()),
            "summary_type": "rolling",
        }

        overlay_lm = lm_with_extra_body(meta)

        with dspy.context(lm=overlay_lm):
            prediction = predictor(
                extra_instructions=instructions,
                previous_summary=previous_summary
                or "Dies ist der erste Abschnitt der Zusammenfasung",
                voice_content=new_transcript,
            )
        summary = prediction.summary.strip()
        
    except Exception as exc:
        logger.error("Error generating rolling summary: %s", exc, exc_info=True)
        return previous_summary or "Summary could not be generated."

    if not summary:
        logger.warning("LLM returned empty rolling summary")
        return previous_summary or "Summary could not be generated."

    logger.info("Generated rolling summary for new transcript chunk")
    return summary

\end{lstlisting}

\subsection{Kommunikation mit dem Frontend}

Nach der Verarbeitung der aktuellen Warteschlange durch das Sprachmodell und der Generierung einer aktualisierten Zusammenfassung werden die resultierenden Analyseergebnisse unmittelbar an das Frontend übertragen. Hierzu wurde eine dedizierte Backend-Komponente in Form des Python-Moduls \texttt{broadcast.py} implementiert, die für die Verteilung der erzeugten Inhalte an alle verbundenen Clients verantwortlich ist.

Die Datenübertragung erfolgt über eine WebSocket-Verbindung, welche eine kontinuierliche und bidirektionale Kommunikation zwischen Backend und Frontend ermöglicht. Sobald eine neue oder aktualisierte Zusammenfassung vorliegt, wird diese automatisch an sämtliche aktiven Verbindungen gesendet. Dieses ereignisbasierte Push-Verfahren gewährleistet eine nahezu echtzeitfähige Darstellung der Analyseergebnisse, ohne dass wiederholte Client-seitige Anfragen erforderlich sind.

Ergänzend kommen klassische REST-Schnittstellen für Steuerungs- und Verwaltungsaufgaben zum Einsatz, beispielsweise zum Initiieren oder Beenden von Analyseprozessen sowie zur Abfrage persistenter Meeting- oder Metadaten. Die Kombination aus REST-Architektur für zustandsbehaftete Operationen und WebSockets für kontinuierliche Datenströme ermöglicht somit eine strukturierte, performante und zugleich flexible Kommunikationsarchitektur zwischen Backend und Frontend.

\begin{lstlisting}[language=python, style=pythonstyle, caption=Erhalten wichtiger Informationen aus dem Frontend, label=lst:startbot]
def broadcast_summary(bot_id: str, summary: str) -> None:
    """
    Broadcast summary update to all WebSocket clients for a given bot.

    Args:
        bot_id: The bot identifier
        summary: The summary text to broadcast
    """
    try:
        channel_layer = get_channel_layer()
        group_name = f"summary_{bot_id}"

        async_to_sync(channel_layer.group_send)(
            group_name,
            {
                "type": "send_summary",
                "summary": summary,
            },
        )
        logger.info(f"Broadcasted summary to group {group_name}")
    except Exception as e:
        logger.error(
            f"Failed to broadcast summary for bot {bot_id}: {e}", exc_info=True
        )
\end{lstlisting}

Die eigentliche Transkription wird durch das Starten der Teams-Transkriptionsfunktion vom Benutzer gestartet. Nach dem Start signalisiert das System den aktuellen Zustand der Verarbeitung. Dabei werden unter anderem die Zustände idle, running, success und error unterschieden, die unmittelbar im Frontend visualisiert werden. Statusänderungen werden direkt über die bestehende WebSocket-Verbindung übermittelt. 

Die interne Zustandsverwaltung der Anwendung erfolgt über React Hooks. Dabei werden unter anderem der aktuelle Verbindungsstatus, die aktive Bot-ID, die Meeting-ID sowie der Zustand der laufenden Transkription gespeichert. Für die WebSocket-Verbindung wird zusätzlich eine Referenz verwendet, um Verbindungsabbrüche bei erneuten Render-Zyklen zu vermeiden und eine stabile Kommunikation sicherzustellen.
