Wichtigste Aufgabe ist das Handling der ankommenden Daten. Nachrichten von Attendee werden an einen Webhook im Backend gesendet. 
In der Ersten Version werden die Nachrichten im View auf ihre Trigger gefiltert. Nachrichten mit dem transcript.update trigger werden in eine Warteschlage hinzugefügt, welche die Gesamtlänge der Nachrichten überwacht. Da es oftmals auch sehr kurze Transkripte gibt, etwa wenn von anderen Teilnehmern eine bestätigung in form eines Ok kommt, werden alle ankommenden transkripte auf ihre länge geprüft und anschließend in eine Warteschlage hinzugefügt. Übersteigt die Gesamtlänge aller Nachrichten einen bestimmten Schwellenwert, in der Ersten Version 10 Sekunden, so wird die gesamte Warteschlange zu einer Nachricht zusammengefasst und zur weiterverarbeitung ans llM geschickt. 
Das ergebnis der Zusammenfassung des LLMs wird als "previous Summary" zwischengespeichert und bei der Nächsten verarbeitung der Warteschlage mit ins llm gegeben um eine koheränte zusammenfassung zu erstellen. 

Anschließend werden die Chunks in der Datenbank gespeichert und über einen Webhook ans Frontend geschickt. Dabei wird immer nur die neuste Nachricht versendet, da diese durch den aufbau der Rolling Summary immer die aktuell vollständige zusammenfassung enthält. 

In der voice App, soll die verarbeitung der Transkriptions-Chunks aus übernommen werden. Dazu wurde zuerst ein Webhook eingerichtet, welcher die von der Attendee API erhaltenen Informationen verarbeitet. 
Ankommende Nachrichten werden je nach trigger unterschiedlich vearbeitet. 
Nachrichten welche über die Transcript.Update message versendet werden, werden an eine Nachrichtenwarteschlange angehängt, nach einer festgelgten gesamtdauer aller nachrichten wird die gesamte queue ans llm geschickt. Mehr dazu im "Kapitel Verarbeitung des Live Transkripts"
